Finite State Machines in Verilog

Turn a state diagram into working hardware with the three-block FSM pattern — built around a complete "1011" sequence detector, the blueprint for Lab 10 and your project.

From diagram to code

Every clocked sequential circuit you analyzed in lecture — state table, state diagram, next-state equations — maps onto one reusable Verilog pattern with three parts:

  • State register (clocked, <=): holds the current state, handles reset.
  • Next-state logic (combinational, =): a case on the current state — this is your state table, row by row.
  • Output logic (combinational): Moore = depends on state only; Mealy = state and inputs.

Name your states with localparam so the code reads like the diagram, not like binary soup.

Complete example: "1011" sequence detector (Moore)

Spec: watching a serial input din one bit per clock, raise found for one cycle when the pattern 1011 has just been seen (overlapping allowed). Five states — one per amount of progress:

seq1011.v — the Lab 10 blueprint
module seq1011(
    input  wire clk, rst,
    input  wire din,
    output wire found
);
    // State encoding: progress through "1011"
    localparam S0   = 3'd0;  // nothing matched yet
    localparam S1   = 3'd1;  // seen 1
    localparam S10  = 3'd2;  // seen 10
    localparam S101 = 3'd3;  // seen 101
    localparam HIT  = 3'd4;  // seen 1011  -> output!

    reg [2:0] state, next;

    // 1) State register  (sequential, non-blocking)
    always @(posedge clk or posedge rst) begin
        if (rst) state <= S0;
        else     state <= next;
    end

    // 2) Next-state logic  (combinational, blocking)
    //    Each case row is one row of the state table.
    always @(*) begin
        next = state;                       // safe default: stay put
        case (state)
            S0:   next = din ? S1   : S0;
            S1:   next = din ? S1   : S10;
            S10:  next = din ? S101 : S0;
            S101: next = din ? HIT  : S10;
            HIT:  next = din ? S1   : S10;  // overlap: "1011" ends in 1
            default: next = S0;
        endcase
    end

    // 3) Output logic (Moore: depends on state only)
    assign found = (state == HIT);
endmodule
  • The default assignment next = state; at the top plus default: in the case means no accidental latches, ever — the Tutorial 3 rule at work.
  • The overlap transitions out of HIT come straight from asking: "after 1011, what prefix of the pattern do the last bits already form?" This is exactly the reasoning from your week 11–12 lectures.
  • Mealy version: make found depend on state and din (e.g. assign found = (state == S101) && din;) — one fewer state, output one cycle earlier.

Testbench with a clock

seq1011_tb.v — feeding the detector a bitstream
`timescale 1ns / 1ps
module seq1011_tb;
    reg  clk = 0, rst, din;
    wire found;

    seq1011 dut (.clk(clk), .rst(rst), .din(din), .found(found));

    always #5 clk = ~clk;        // 100 MHz clock: toggle every 5 ns

    // Drive one bit per clock, changing din just after each edge
    task send(input b);
        begin din = b; @(posedge clk); #1; end
    endtask

    initial begin
        rst = 1; din = 0; @(posedge clk); #1; rst = 0;
        // stream: 1 0 1 1 0 1 1  -> hits after bit 4 and (overlap) bit 7
        send(1); send(0); send(1); send(1);
        send(0); send(1); send(1);
        #20 $finish;
    end
endmodule

In the waveform, confirm found pulses exactly twice. This clock-generator idiom (always #5 clk = ~clk;) is the template for every sequential testbench you'll write, including the project.

On the board: buttons need conditioning

To demo the detector with a pushbutton as din and another as the "clock," you'd suffer from bounce and from holding buttons across many real clock cycles. The Lab 10 handout provides a debounce + single-pulse module; the FSM itself stays clocked at 100 MHz and treats the conditioned button as a one-cycle din_valid enable. Design rule: never clock an FSM from a button — condition the button into an enable instead.
